# Безопасность

## Этот репозиторий публичный

В нём **никогда** не должно быть:

| Что | Где живёт на самом деле |
|---|---|
| SSH-ключи сервера | у владельца и разработчиков, `~/.ssh/` |
| Пароль SMTP и прочие пароли | `/etc/systemd/system/music.service.d/*.conf` на сервере (права 600) |
| Почты администраторов | `/etc/systemd/system/music.service.d/admins.conf` на сервере |
| Cookies аккаунтов YouTube | `/var/lib/music/ytaccounts/` на сервере, загружаются через админку |
| Токен Яндекс Музыки | `/etc/systemd/system/music.service.d/yandex.conf` на сервере (права 600), берётся `ops/yandex-token.sh` |
| Ключ подписи Android, `keystore.properties` | у владельца, `~/.android-keys/` |
| База `music.db`, её бэкапы, логи сервера | только на сервере |
| Почты, токены и любые данные пользователей | только в базе |

В примерах — только заглушки (`ops/systemd/*.example`, `admin@example.com`).
`.gitignore` закрывает типичные файлы секретов (`*.jks`, `keystore.properties`, `cookies*.txt`, `*.pem`, `*.db`, `.env`),
но последняя линия обороны — проверка диффа перед коммитом:

```bash
git diff --cached | grep -nE "PRIVATE KEY|PASS=|password|token|SAPISID|@gmail|@yandex"
```

## Если секрет попал в коммит

1. **Сразу сменить секрет** (пароль, ключ, cookies) — после публикации он считается утёкшим, даже если коммит удалить.
2. Потом убрать из истории (`git filter-repo`) и сделать force-push по согласованию с владельцем.

## Как устроена защита сервиса

- Аудио (`/api/stream`) и всё API, кроме входа, регистрации и публичных плейлистов, — только с сессией.
- Пароли — argon2; сессии — случайные 256-битные токены, cookie `HttpOnly; Secure; SameSite=Lax`, 60 дней с последнего входа.
- Антибрутфорс на вход, регистрацию и сброс пароля.
- Админка — только почты из `MUSIC_ADMINS`, права проверяются на каждом запросе к `/api/admin/*`.
- Caddy: HTTPS, HSTS, строгий CSP, `X-Frame-Options: DENY`; бэкенд слушает только `127.0.0.1`.
- SSH на сервер — только по ключу.
